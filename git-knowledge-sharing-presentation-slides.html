Distributed Version Control

Git is a snapshot graph every developer can carry locally.

Each developer has a full local repository with history. The remote repository coordinates collaboration, but most Git operations happen on your machine.

Developer A Working tree + full local history 
git clone
git commit
git push
Developer B Can branch, inspect, compare, and commit offline 
git fetch
git pull
git merge
Developer C Own copy of commits, branches, tags, and refs 
git log --oneline
git diff
Remote Repository GitHub, GitLab, Bitbucket, or internal Git server
What changed?

Diffs explain file-level changes between snapshots.

Why changed?

Commit messages and pull requests preserve intent.

Can we go back?

History, tags, revert, and reflog give recovery paths.

Three States

Git separates editing, selecting, and recording.

This separation lets you group related work into clear commits instead of saving every file change automatically.

Working Directory Files on disk. New edits start here. 
git diff
git restore file.ts
Staging Area The next commit is assembled here. 
git add file.ts
git diff --staged
Local Repository Committed snapshots live in history. 
git commit -m "Fix login"
git log --oneline

Inspection command

git status is the dashboard for all three states: changed, staged, untracked, and branch position.

Selective commits

Stage only related files or hunks so each commit tells one coherent story.

Daily Collaboration

The basic workflow is a small feedback loop.

Most teams work through short-lived branches, pull or merge requests, review, CI, and protected merges.

clone branch change add commit push pull request review merge 
git clone <repo-url>
git switch -c feature/login-page
git status
git add src/Login.tsx
git commit -m "Add login page"
git push -u origin feature/login-page

Team habits matter

  • Small pull requests
  • Consistent branch names
  • Useful commit messages
  • CI before merge
  • Protected main branch

Branching Strategies

Choose the branch model that matches release reality.

The best strategy is less about Git fashion and more about deployment frequency, release control, test confidence, and team size.

Trunk-Based Development

main |- short-lived feature |- short-lived bugfix `- feature flags hide incomplete work
Pros
  • Fast integration
  • Fewer stale branches
  • Great with CI/CD
Cons
  • Needs discipline
  • Needs strong tests
  • Often needs flags
Use when
  • Deploy often
  • Small PRs
  • Main stays healthy

Git Flow

main `- develop |- feature/* |- release/* `- hotfix/*
Pros
  • Clear release stages
  • Explicit hotfixes
  • Governance-friendly
Cons
  • More ceremony
  • Slower integration
  • Long-lived branches
Use when
  • Scheduled releases
  • Versioned products
  • Regulated delivery

GitHub / GitLab Flow

main |- feature/* |- bugfix/* `- hotfix/*
Pros
  • Simple
  • PR-centered
  • Easy to teach
Cons
  • Main must be stable
  • CI discipline required
  • Release gates are external
Use when
  • Web apps
  • Protected main
  • Frequent deploys

Release Branches

main |- feature/* `- release/2026.05 `- stabilization fixes only
Pros
  • Stabilize release
  • Development continues
  • Patchable line
Cons
  • Cherry-pick overhead
  • Stale branch risk
  • Needs rules
Use when
  • QA/UAT cycle
  • Controlled deploy
  • Bundled releases

Strategy Recommendation

A pragmatic default for most product teams.

Default

GitHub / GitLab Flow

Branch from main, open a PR/MR, review, pass CI, merge. Good balance of simplicity and control.

Advanced

Trunk-Based + Flags

Use when the team can integrate continuously and hide unfinished work behind feature flags.

Heavy release

Git Flow / Release Branches

Use when release timing, stabilization, or governance is more important than integration speed.

High release frequencyPrefer trunk-based or GitHub Flow
Strong CI and flagsShorten branch lifetime
Controlled release gatesUse release branches or Git Flow

Git Hooks

Shift quality checks earlier without making commits painful.

Hooks are scripts that run at specific Git events. Keep local hooks fast and reliable; move slow full validation into CI.

Write code

Edit files locally.

pre-commit

Format, lint, type check, secret scan.

commit-msg

Validate message style such as Conventional Commits.

pre-push

Run heavier local tests before sending work upstream.

CI

Run full build, test, security, and deployment gates remotely.

npm install husky --save-dev
npx husky init
echo "npm run lint" > .husky/pre-commit

A good hook is

  • Fast enough for daily use
  • Reliable on every developer machine
  • Clear when it fails
  • Useful enough to justify blocking

Conflict Resolution

A conflict is Git asking for a human decision.

Git can merge most changes. It stops when both sides changed the same line or nearby lines and there is no safe automatic choice.

<<<<<<< HEAD
const title = "Sign In";
=======
const title = "Member Login";
>>>>>>> feature/member-login

Resolution loop

  • Open conflicted files
  • Remove conflict markers
  • Keep or combine the correct code
  • Stage resolved files
  • Continue merge or rebase
git status
git add src/Login.tsx
git merge --continue
git merge --abort
git status
git add src/Login.tsx
git rebase --continue
git rebase --abort

Undo Decision Tree

Pick the undo command based on sharing risk.

The key question is whether the change has already been pushed or pulled by someone else.

Has the change been pushed or shared?

Shared history should be preserved. Local private history can be rewritten more freely.

No, still local
  • git commit --amend fixes the last commit
  • git restore --staged file unstages
  • git restore file discards file edits
  • git reset --soft HEAD~1 keeps changes staged
  • git reset HEAD~1 keeps changes unstaged
Yes, shared
  • git revert <commit> creates a new undo commit
  • Avoid rewriting public history
  • Use --force-with-lease only when the team agrees
  • Be very careful with git reset --hard
git add missing-file.ts
git commit --amend --no-edit
git reset --soft HEAD~1
git revert abc1234
git push origin main

Command-Line Help

You do not need to memorize Git. You need to know where Git explains itself.

Manual entry point

man git

Start with the general Git manual.

Command manual

git help rebase

Open full docs for a specific command.

Quick flags

git commit -h

See concise option help in the terminal.

Inside man pages

  • Space next page
  • b previous page
  • /word search
  • n next result
  • q quit

Closing rule

Use history rewriting for local cleanup. Use review, CI, protected branches, and revert for shared collaboration.

Clear Git habits reduce review cost, conflict cost, and release risk.
